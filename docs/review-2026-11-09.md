## 1. Резюме

Проект в целом в хорошем состоянии. Backend — самая зрелая часть: аккуратная работа с SQLite, транзакциями, очередями, путями и безопасностью; 492 тестовые функции, тесты проходят. Web — полноценный клиент с zod-валидацией на границе API, TanStack Query, PWA, ТВ-режимом и 216 unit-тестами. Mobile — пока только каркас по плану `mobile-shared-core`.

Главные риски:

1. **Потеря данных в backend.** `ExtractService` при ошибке извлечения может удалить уже существующий итоговый аудиофайл. Сканер при исчезновении файлов делает необратимый hard-purge записей вместе с избранным, прогрессом и элементами коллекций.
2. **Docker не запускается «из коробки».** Образ, compose и healthcheck ждут порт `8095`, пример конфига — `8080`.
3. **Web не готов к отдельному деплою.** `VITE_API_BASE` поддерживается только для JSON API; все stream/thumb/cover/subs/download URL захардкожены на `/api/...`, а cookie-сессия с `SameSite=Lax` кросс-сайт не работает.
4. **Функциональный баг в web.** Кнопка «В очередь» на экране видео добавляет видео в аудио-плеер.
5. **Крупный продуктовый пробел.** Legacy-фича offline/downloads не перенесена ни в web, ни в mobile.
6. **Документация рассогласована.** Актуальны только `mobile-shared-core` план/спека и, как reference, продуктовые спеки. Остальные планы — исторические Flutter-инструкции. `backend/docs/...` устарел и при этом tracked.

Общая оценка:

| Область | Качество | Готовность |
|---|---|---|
| Backend | высокое | production-ready с оговорками по data-loss сценариям |
| Web | высокое | уверенный beta; не хватает offline, bulk и части video-фич |
| Mobile | каркас | 1-й этап плана выполнен, приложение ещё не является клиентом |
| Shared | каркас | транспорт/health/query готовы; модели и API-модули не переехали |
| Docs | смешанное | один актуальный план, остальное — архив/мусор |

## 4. Backend

### 4.1 Сильные стороны

- Чёткое разделение `handlers → services → repository`, DI и lifecycle в [app.go](../backend/internal/app/app.go).

- Очереди upload/extract/transcode: персистентность, восстановление после рестарта, отмена, идемпотентная очистка.

### 4.2 Находки

#### B-01 — P0: `ExtractService` удаляет существующий итоговый файл при ошибке

**Где:**
- [extract.go:496](../backend/internal/services/extract.go#L496-L498) — `job.outPath = dstPath`;
- [extract.go:514](../backend/internal/services/extract.go#L514-L520) — при ошибке ffmpeg удаляется `tmpPath` и вызывается `q.fail`;
- [extract.go:807](../backend/internal/services/extract.go#L807-L815) — `fail` вызывает `cleanupJob(outPath, mediaID)`, то есть удаляет `dstPath`.

**Сценарий:**
1. В `audio/` уже лежит `Название.m4a` (например, извлечённый ранее трек).
2. Пользователь извлекает аудио из другого видео с тем же названием.
3. `dstPath` совпадает с существующим файлом.
4. ffmpeg падает (битый кодек, нет места, отмена).
5. Код удаляет `tmpPath`, затем `fail` удаляет `dstPath` — **существующий трек потерян**.

**Почему важно:** это тихая потеря пользовательского файла, не связанная с действиями пользователя. Ошибка не видна в БД: запись остаётся, файла нет.

**Что сделать:**
- До успешного `commitFile` `job.outPath` должен указывать на `tmpPath` (или быть пустым).
- После `commitFile` — на `finalPath`.
- В `fail`/`cleanupJob` различать «временный файл» и «закоммиченный результат».
- Добавить регрессионный тест: существующий `dstPath` + ошибка ffmpeg → файл на месте.

**Критерий готовности:** тест воспроизводит сценарий и проходит; `git grep outPath` не содержит пути, который может указывать на чужой файл до коммита.

#### B-02 — P0: Сканер делает hard-purge записей при исчезновении файлов

**Где:**
- [scanner.go:195](../backend/internal/services/scanner.go#L195-L227) — `sweepDeleted` вызывает `PurgeMedia` для всех записей, чьих файлов нет в `seen`;
- [media.go:511](../backend/internal/repository/media.go#L511-L540) — `PurgeMedia` hard-delete’ит медиа и каскадно избранное, прогресс, элементы коллекций, субтитры, связи артистов;
- [scanner.go:341](../backend/internal/services/scanner.go#L341-L365) — watcher при `Remove/Rename` делает то же самое, но хотя бы чистит превью и обложки;
- [scanner.go:211](../backend/internal/services/scanner.go#L211) — `sweepDeleted` не удаляет `thumbnails/<id>.jpg` и `<id>_cover.*`, поэтому файлы остаются навсегда.

**Сценарии:**
- Сетевой mount на секунду отвалился или оказался пустым — библиотека «исчезла», все пользовательские связи уничтожены.
- Файл переименован/перемещён — история, избранное и коллекции потеряны без корзины.
- Файл удалён с диска — превью и обложка остаются мусором.

**Что сделать:**
- Не делать hard-purge по факту отсутствия файла. Помечать запись `AutoTrashed` и убирать в корзину, не трогая пользовательские связи.
- Превью/обложки при soft delete НЕ удалять: они нужны для восстановления. Окончательно чистит `PurgeMedia` из корзины.
- Purge `AutoTrashed`-строки не должен удалять файл: он мог вернуться (mount, переименование). Пользовательская корзина (`AutoTrashed=false`) удаляет файл как раньше, но только если на путь не ссылается другая строка.
- Если файл вернулся на тот же путь, восстанавливать ту же `AutoTrashed`-строку и обновлять её, а не создавать вторую живую запись. Пользовательскую корзину не воскрешать.
- Поиск по пути (`FindByPath`/`FindByPathBasic`) должен возвращать живую строку раньше trashed.
- Тесты: файл исчез → `AutoTrashed` в корзине, связи/превью целы; файл вернулся → та же строка живая, дублей нет; пользовательская корзина не воскрешается; purge `AutoTrashed` и purge при второй строке на путь не удаляют файл.

**Критерий готовности:** исчезновение файла не удаляет избранное/прогресс/коллекции; после окончательного purge превью и обложки не остаются сиротами.

#### B-03 — P1: Очистка метаданных невозможна, контракт врёт

**Где:**
- [metadata.go:91](../backend/internal/handlers/metadata.go#L91-L92) — комментарий: «values can also be cleared»;
- [metadata.go:139](../backend/internal/handlers/metadata.go#L139-L166) — поля присваиваются, включая пустые;
- [media.go:335](../backend/internal/repository/media.go#L335-L389) — `Update` пишет только непустые значения (`if media.Title != ""`, `if media.Year != 0`, ...);
- [metadata.go:168](../backend/internal/handlers/metadata.go#L168-L170) — при любом обновлении создаётся `Metadata{}`, даже если менялся только title.

**Следствия:**
- Очистить `title`, `description`, `album`, `genre`, `year` через API нельзя.
- Пустой `title` в запросе молча игнорируется: клиент получает старое значение.
- У медиа появляются пустые строки `Metadata`.

**Что сделать:**
- Ввести patch-семантику на уровне репозитория: `*string`/`*int` для полей, где `nil` — «не трогать», `""`/`0` — «очистить».
- Либо явно запретить очистку в API и убрать ложный комментарий/поведение.
- Не создавать `Metadata`, если ни одно поле метаданных не менялось.
- Покрыть тестами: очистка description, очистка year, обновление только title.

**Критерий готовности:** контракт API совпадает с поведением; пустые значения можно осознанно записать или они отвергаются с 400.

#### B-05 — P2: Превью и обложки пишутся сразу в финальный файл

**Где:**
- [thumbnail.go:115](../backend/internal/services/thumbnail.go#L115-L151) — видео-превью;
- [thumbnail.go:161](../backend/internal/services/thumbnail.go#L161-L194) — превью картинок;
- [thumbnail.go:209](../backend/internal/services/thumbnail.go#L209-L248) — извлечение встроенной обложки.

**Проблема:** ffmpeg получает финальный путь и `-y`. При падении/таймауте может остаться частичный или пустой файл. `ThumbHandler.Get` проверяет только `Exists`, поэтому клиент получит битую картинку. Для видео-превью при изменении файла это ещё и затирает предыдущее валидное превью.

**Что сделать:** писать в `*.tmp`/`.part`, проверять размер и сигнатуру, затем `os.Rename`/`commitExclusive`. При ошибке удалять tmp и не трогать старый файл.

**Критерий готовности:** сбой ffmpeg не меняет существующее превью и не оставляет файл, который отдаётся как валидный.

#### B-06 — P2: Transcode оставляет запись при ошибке thumbnail

**Где:** [transcode_queue.go:681](../backend/internal/services/transcode_queue.go#L681-L689).

После `media.Create` ошибка обновления `thumbnail_url` вызывает `q.fail`, но `removeResult(media)` не вызывается. При ретрае источник ещё есть, а в библиотеке уже лежит запись без превью; повторная обработка может привести к дублю или ложному «файл уже существует».

**Что сделать:** при ошибке после создания результата вызывать `removeResult(media)` (как в ветках ошибок субтитров) либо явно оставлять запись и завершать задачу успехом без превью.

#### B-08 — P2: Rate limiter не работает за reverse proxy

**Где:** [app.go:735](../backend/internal/app/app.go#L735-L742).

`getClientIP` возвращает `c.IP()` и сознательно не читает `X-Forwarded-For`. За Nginx/Traefik/Caddy все клиенты выглядят как один IP, поэтому:
- лимиты душат всех сразу;
- невозможно отличить атакующего от обычных пользователей.

## 6. Mobile и `packages/shared`

### Что готово

Каркас полностью соответствует плану `mobile-shared-core`:

- npm workspaces, `@flux/shared` с `ApiConfig`/`AuthTransport`/`KeyValueStore`, общий `queryClient`, health-хук;
- Expo + expo-router, Metro с `watchFolders`, `expo-secure-store`, экран health и экран настроек с сохранением URL сервера;
- web переведён на shared для `client.ts`/`health.ts`/`queryClient.ts` — тонкие реэкспорты.

Typecheck и lint mobile/shared проходят. В shared 17 тестов; в этой песочнице они не запустились из-за read-only кэша — это ограничение окружения, не кода.

### M-01 — P1: Модели и API-модули не переехали в shared

**Где:** [packages/shared/src/index.ts](../packages/shared/src/index.ts) экспортирует только транспорт, health, query и storage. [web/src/core/README.md](../web/src/core/README.md) прямо говорит, что папка должна переехать в общий пакет.

Сейчас web-модели (`Media`, `Subtitle`, `mediaSchema`), fetch-функции и форматтеры живут в `web/src/core`; mobile их не может использовать. Следующий шаг — перенести `web/src/core` → `packages/shared` (код уже чистый TS без DOM), а web-импорты сделать реэкспортами. Иначе mobile начнёт дублировать схемы и запросы.

**Критерий готовности:** `import { mediaSchema, fetchMediaById } from "@flux/shared"` работает в web и mobile; в `mobile/` нет собственных копий API-схем.

### M-02 — P1: Нет auth, экранов, i18n, тестов

Mobile — это health-экран + настройки. Нет:
- login/OTP/refresh UI;
- списка медиа, плеера, коллекций, загрузки;
- i18n (строки захардкожены по-русски);
- тестов (0 файлов).

Это соответствует «первому шагу» плана, но до клиента ещё далеко. Следующий этап: auth-экран, затем перенос `web/src/core` и базовые списки.

### M-03 — P2: При неудачном refresh токены не очищаются

**Где:** [transport.ts:51](../packages/shared/src/api/transport.ts#L51-L84).

`createTokenTransport.refresh` при не-ok ответе бросает ошибку, но не удаляет access/refresh из `KeyValueStore`. После протухания сессии приложение останется с мёртвыми токенами до ручного logout.

**Что сделать:** при 401/400 на refresh очищать оба ключа и отдавать событие «сессия истекла» для навигации на login.

### M-04 — P2: Нет тестов и проверок сборки

CI для mobile делает только `typecheck` и `lint`. Нет ни unit-тестов, ни smoke-сборки (`expo export`/`expo-doctor`). Для каркаса допустимо, но перед экранами нужно добавить хотя бы тесты на transport/storage и smoke-сборку.

### M-05 — P3: `versionCode` и версия пакета живут отдельно

`mobile/package.json` — `0.1.3`, `app.json` — `versionCode: 21`. По AGENTS патч-версия бампается в `package.json`, но Android `versionCode` надо не забыть поднять вручную; иначе APK не встанет поверх старого. Стоит автоматизировать (скрипт/CI).

## 9. Корень, `node_modules`, CI, Docker

### 9.1 Почему `node_modules` в корне

Это не случайность. В [package.json](../package.json) объявлены npm workspaces (`web`, `mobile`, `packages/shared`), npm hoist’ит зависимости в корневой `node_modules`, там же единый [package-lock.json](../package-lock.json). Для workspaces это нормальная схема.

Но 9.9 ГБ — раздутие:

- `node_modules/react-native-reanimated/android` — ~6.0 ГБ;
- `node_modules/react-native-worklets/android` — ~3.3 ГБ;
- `node_modules/expo-modules-core/android` — ~2.9 ГБ.

Это результаты Gradle-сборки, а не исходники. Лечится `rm -rf node_modules && npm ci` (или удалением `node_modules/*/android/build`).

### 9.2 Что действительно лишнее

- **`jsdom` в корневом `package.json`** ([package.json:6](../package.json#L6-L9)) — он уже есть в `web/devDependencies`; корневой дубль не нужен.
- **`web/node_modules` (626 МБ) и `packages/shared/node_modules`** — остатки локальных установок; после `npm ci` из корня должны схлопнуться.
- **`frontend/build` (1.7 ГБ), `frontend/.dart_tool` (305 МБ), `mobile/android` (1.5 ГБ)** — генерируемые артефакты, в git не входят; можно удалить локально.
- **`frontend/android/build/reports/problems/problems-report.html`** — единственный tracked артефакт сборки (нашёл в `git ls-files`). `git rm --cached` + `frontend/android/build/` в `frontend/.gitignore`.
- **`backend/.dockerignore`** — мёртвый: Docker-контекст задаётся из корня ([docker-compose.yaml](../backend/docker-compose.yaml)), поэтому применяется корневой [.dockerignore](../.dockerignore).
- **`.dockerignore` не исключает `mobile/` и `docs/`** ([.dockerignore:7](../.dockerignore#L7-L10)); `mobile/android` 1.5 ГБ попадает в контекст, хотя Dockerfile его не использует.
- **`package-lock.json` содержит один пакет с `registry.npmmirror.com`** ([package-lock.json:2482](../package-lock.json#L2482-L2486)), остальные 966 — npmjs. Если это не осознанное зеркало, lock надо перегенерировать с `--registry=https://registry.npmjs.org`.
- В `git status` висят `AGENTS.md` и `package-lock.json`; в lock уже попали бампы `web 0.1.22` / `mobile 0.1.3`, но они не закоммичены.

### 9.3 CI

[.github/workflows/ci.yml](../.github/workflows/ci.yml):

- Backend job использует Go 1.23 при `go 1.25.0` в `go.mod`.
- Frontend job всё ещё собирает и тестирует **legacy Flutter** — если `frontend/` заморожен, job надо убрать.
- Web job не запускает e2e, `knip` и `size-limit`.
- Нет сборки Docker-образа, поэтому рассинхрон портов/workspace-зависимостей не ловится.
- Нет проверки `git diff` после генерации `routeTree.gen.ts`.

`Makefile` стоит привести к текущей структуре (`backend`, `web`, `mobile`, `shared`) или удалить legacy-таргеты.
